# Аналіз записів логічного аналізатора — ЛР2

Записи зроблено компонентом `wokwi-logic-analyzer` (8 каналів, внутрішня роздільність 1 ГГц, VCD з кроком 1 нс;
модель STM32C0 у Wokwi квантує фронти з кроком 25 нс). Вирізки, експорт анотацій і `measurements.json`
генерує `tools/la_analyze.py`. Ті самі вирізки збережено у форматі сесії PulseView (`*.sr`).

| Файл (вирізка) | Інтерфейс / сценарій | Частота дискретизації при декодуванні | Канали |
|---|---|---|---|
| `i2c_mpu6050_whoami-burst14` | I²C: WHO_AM_I + багатобайтове читання 0x3B..0x48 | 50 МГц (downsample 20) | SCL, SDA |
| `i2c_mpu6050_hw-read-stall_anomaly` | I²C: HAL_I2C_Mem_Read у Wokwi — аномалія §A1 | 50 МГц | SCL, SDA |

| `spi_w25q64_jedec-wren-erase-pp-read` | SPI: 9Fh, 05h, 06h, 20h, BUSY, 06h+02h, 03h | 50 МГц | SCK, MOSI, MISO, CS# |

**Вибір частоти дискретизації.** Для декодування потрібно щонайменше 4 відліки на найкоротший біт, бажано 8–10:
* SPI 3 МГц: напівперіод SCK = 167 нс → ≥ 24 МС/с. Взято 50 МС/с (≈ 8 відліків на напівперіод).
* I²C 100 кГц: ≥ 1 МС/с, взято 50 МС/с, щоб виміряти t_SU/t_HD.
* UART 115200: біт 8.68 мкс → ≥ 0.5 МС/с, взято 10 МС/с.
* PWM 50 Гц з роздільністю 1 мкс: 1 МС/с.

Wokwi пише всю сесію (тригер не потрібен). Глибина запису: модель зберігає лише зміни (9 Б/подія), тож сесія A
на 6.3 с = 0.24 МБ VCD. Реальний аналізатор на базі FX2 при 24 МС/с і 8 каналах пише ~24 МБ/с, тобто сесія на 6.3 с
займе ~150 МБ без стиснення. Тому на реальному стенді частоту дискретизації варто підбирати під
найшвидшу шину запису, а тригер ставити на CS#↓ (SPI), SDA↓ при SCL=1 (I²C START) або PB0↑ (ADC).

## A. I²C — MPU-6050 (0x68)

### A0. Декодована послідовність (soft-I²C, `cap i2c`, файл `.ann.txt`)

```
S | 68+W ACK | 75 ACK | Sr | 68+R ACK | 68 NACK | P                            ← WHO_AM_I
S | 68+W ACK | 3B ACK | Sr | 68+R ACK | E0 00 00 00 37 6C EF 5C 00 00 00 00 00 00(NACK) | P
```

**Зіставлення з datasheet** (PS-MPU-6000A, розд. 9.3 «I²C Communications Protocol», рис. «Burst Read Sequence»):
master: S, AD+W, RA, Sr, AD+R, далі ACK після кожного байта, крім останнього (NACK), і P. На шині все
збігається: 13 ACK і NACK на 14-му байті, автоінкремент адреси регістру з 0x3B до 0x48.

Розбір 14 байтів (RM-MPU-6000A, розд. 4.17–4.19):

| Регістри | Байти | int16 | Фізично | Модель Wokwi (`diagram.json`) |
|---|---|---|---|---|
| ACCEL_X | E0 00 | −8192 | −8192 / 16384 = **−0.500 g** | accelX = −0.5 |
| ACCEL_Y | 00 00 | 0 | 0 g | 0 |
| ACCEL_Z | 37 6C | 14188 | **0.866 g** | 0.866 |
| TEMP | EF 5C | −4260 | −4260/340 + 36.53 = **24.00 °C** | 24 |
| GYRO_X/Y/Z | 00 00 ×3 | 0 | 0 °/с | 0 |

|a| = √(0.5² + 0.866²) = 1.000 g. Кут pitch = atan2(0.5, 0.866) = **30.0°**; телеметрія в режимі MIRROR показує `pitch=30`,
а серво tilt виходить на 1667 мкс = 1500 + 30·500/90. Ці самі байти — тестовий вектор у `tests/la_vectors.h`
(генерується `tools/extract_vectors.py`). Тест подає їх у драйвер через fake-шину й отримує ті самі
`raw=-8192,0,14188,-4260,0,0,0`, що прошивка вивела в UART.

### A0.1 Ручне декодування за формою сигналу (рис. `la-i2c-manual.png`)

| Подія | Ознака на SCL/SDA | Біт |
|---|---|---|
| START | SDA ↓ при SCL = 1 (t = 15 мкс у вирізці) | — |
| A6…A0 | значення SDA на фронтах ↑ SCL №1–7 | 1 1 0 1 0 0 0 = 0x68 |
| R/W | фронт ↑ SCL №8 | 0 = запис → байт адреси 0xD0 |
| ACK | фронт ↑ №9: SDA утримує **slave** (MPU-6050) у 0 | 0 = ACK |
| D7…D0 | фронти ↑ №10–17 | 0 1 1 1 0 1 0 1 = 0x75 (WHO_AM_I) |
| ACK | фронт ↑ №18 | 0 |

Дані змінюються лише коли SCL = 0, а SCL = 1 означає «дані стабільні». Єдині зміни SDA при SCL = 1 —
це START/STOP. Цим I²C відрізняється від SPI (див. §B).

### A1. Аномалія: апаратний I2C STM32C0 у Wokwi не виконує фазу читання

Файл `i2c_mpu6050_hw-read-stall_anomaly`, рис. `la-i2c-hw-anomaly.png`. Декодовано:
`S | 68+W ACK | 75 ACK |` — і далі **нічого**: ні repeated START, ні адреси 0xD1, ні тактів SCL, ні STOP.
HAL при цьому повертає `HAL_ERROR`, `HAL_I2C_GetError() = 0x20` (= `HAL_I2C_ERROR_TIMEOUT`). Self-test пише
`ST;I2C1;hw_read;WARN;timeout err=0x20 id=0x00`.

**Розбіжність між HAL і шиною.** HAL «думає», що чекає на прапор TC/RXNE, а на шині транзакція завершилася
на ACK після 0x75 і лінія лишилася в стані «зайнята» (STOP не було). Дефект належить моделі симулятора:
I²C-скан (`HAL_I2C_IsDeviceReady`, лише фаза запису адреси) працює, а читання — ні. Те саме спостерігалося
в ЛР1 (журнал ЛР1, проблема 5).
Обхід: self-test перемикає вказівник `imu.bus` на bit-bang реалізацію `plat_i2c_sw()` на тих самих пінах.
Драйвер при цьому не змінюється, а на реальній платі fallback не спрацює. Наслідок для реального заліза:
після такого обриву slave може тримати SDA в 0. Для цього в ЛР3 варто додати процедуру bus recovery
(9 тактів SCL + STOP, UM10204 розд. 3.1.16).

### A2. Навмисна аномалія: NACK на неіснуючу адресу 0x69

Команда `cap nack` надсилає той самий запит WHO_AM_I на адресу 0x69 (так виглядало б AD0 = 3V3).
На шині: `S | 69+W NACK | P` за **123 мкс**. На 9-му такті SDA лишається в 1, бо slave не тягне лінію
(UM10204 розд. 3.1.6). Драйвер повертає `BUS_NACK (-1)`, а прошивка пише `CAP;nack;addr=0x69;st=-1`.
Зверніть увагу: master **одразу** видає STOP, а не намагається надіслати регістр. Саме це перевіряє тест
`test_init_nack_wrong_address`.

## B. SPI — W25Q64 (CS# = PB10)

Декодовано (`spi_..._read.ann.txt`, рис. `la-spi-sequence.png`). Кожен рядок — один інтервал CS# low:

```
#0   MOSI 9F FF FF FF      MISO FF EF 40 17          JEDEC ID = EF 40 17 ✔
#1   05 FF                  FF 00                     SR1 = 00 (не BUSY, WEL=0)
#2   06                     FF                        WRITE ENABLE
#3   05 FF                  FF 02                     SR1 = 02 → WEL=1 ✔
#4   20 00 20 00            FF FF FF FF               SECTOR ERASE 0x002000
#5…#27  05 FF              FF 03  (×23, кожні 2 мс)  BUSY=1, WEL=1 — стирання триває
#28  05 FF                  FF 00                     готово: 45.7 мс від CS#↑ команди 20h
#29  06 / #30 05 FF → 02    WREN + перевірка WEL
#31  02 00 20 00 4C 52 32 2D 53 50 49 21              PAGE PROGRAM «LR2-SPI!» у 0x002000
#32  05 FF → 03; #33 05 FF → 00                       BUSY < 1.4 мс (крок опитування)
#34  03 00 20 00 FF×8       … 4C 52 32 2D 53 50 49 21 READ → «LR2-SPI!» ✔   (усього 35 інтервалів CS#)
```

**Зіставлення з datasheet** (W25Q64JV, «Instruction Set Table 1» і діаграми інструкцій): опкод, далі 24-бітна
адреса старшим байтом уперед, далі дані. **WREN (06h) — в окремому інтервалі CS#**: запис/стирання
приймаються лише при WEL = 1, а виконання стартує по CS#↑ після останнього байта. Після завершення WEL
скидається сам. Усе це видно на записі: після стирання й програмування SR1 повертається з 03 у 00.
Під час байта команди на MISO лежить FF, бо відповідь починається лише з наступного байта (рис., 1-ша панель).

**SPI mode 0 (CPOL = 0, CPHA = 0).** SCK у спокої = 0. MOSI змінюється до першого фронту ↑ і по кожному спаду SCK,
а обидві сторони захоплюють дані по фронту ↑. Декодер sigrok з `cpol=0:cpha=0` дає коректні байти
(EF 40 17). З `cpha=1` той самий запис дає MISO = `DE 80 2F`, тобто байти зсунуті на біт (перевірено sigrok-cli). MOSI = `9F` при цьому
декодується правильно лише тому, що модель виставляє біт задовго до обох фронтів.
Контрольне питання 5 відповідає саме на це: режим підтверджено записом.

| Параметр | Розрахунок | Виміряно |
|---|---|---|
| f_SCK | 48 МГц / 16 = 3.0 МГц (333 нс) | 325–350 нс, середнє 336 нс (2.98 МГц) |
| Тривалість байта (8 тактів) | 2.67 мкс | 2.35 мкс (від 1-го до 8-го фронту ↑) |
| Пауза між байтами всередині транзакції (tx-only) | — | **4.6 мкс** (після виправлення, див. нижче) |
| Пауза між байтами (rx, HAL_SPI_TransmitReceive) | — | 17.4 мкс |
| CS#↓ → перший фронт SCK (t_SLCH, W25Q64 ≥ 5 нс) | — | 19 мкс |
| Останній SCK → CS#↑ (t_CHSH ≥ 5 нс) | — | 44 мкс |
| CS# high між інструкціями (t_SHSL ≥ 10 нс для читання, ≥ 50 нс для запису) | — | ≥ 10 мкс |
| tSE (Sector Erase), модель | 45 мс (тип.), ≤ 400 мс | BUSY ≈ 45.7 мс |
| tPP (Page Program), модель | 0.4 мс (тип.), ≤ 3 мс | BUSY ≤ 1.3 мс (обмежено кроком опитування 1 мс SysTick) |

**Знахідка B3: побайтові виклики HAL.** У першій версії `spi_transfer()` викликав `HAL_SPI_TransmitReceive`
для кожного байта окремо. Запис `raw-profileA-boot.vcd` показує паузу **56–115 мкс (медіана 60 мкс)** між
байтами при тривалості байта 2.4 мкс, тобто реальна пропускна здатність була ~16 КБ/с замість 375 КБ/с.
Після переходу на один виклик HAL на буфер медіана паузи впала до **4.6 мкс**. Залишкові паузи —
це програмне опитування FIFO в HAL на Cortex-M0+. Для ЛР3 (запис траєкторії 50 Гц × 8 Б) цього достатньо,
а для великих обсягів знадобиться DMA.

**Спостереження B4: MISO при CS# high.** Між транзакціями MISO на записі = 0. Модель переводить DO у вхід
(High-Z), а аналізатор Wokwi показує незведену лінію як 0. На реальному стенді лінія «плаватиме». Через це
перший MISO-байт першої транзакції в ранньому записі декодувався як `7F` замість `FF`: модель почала
керувати DO вже після першого фронту SCK. На залізі цю проблему знімає pull-up 10–100 кОм на MISO або
ігнорування MISO під час байта команди (драйвер так і робить: `rx = NULL` для заголовка).

## D. PWM — TIM3_CH1/CH2 (серво)

Self-test виставляє pan = 1000 мкс, потім 2000 мкс, по 60 мс (3 періоди) кожне (`pwm_..ann.txt`, рис. `la-pwm.png`):
декодер `pwm` дає duty 5.000 % → 1000/20000 і 10.000 % → 2000/20000.

| Параметр | Розрахунок | Виміряно |
|---|---|---|
| Період | (ARR+1)/1 МГц = 20.000 мс | 20.000 мс (min 19.99998, max 20.00575 — див. нижче) |
| Ширина при CCR = 1000 / 1500 / 2000 | 1000 / 1500 / 2000 мкс | 1000.0 / 1500.0 / 2000.0 мкс |
| Потенціометр 2050 → CCR | 1000 + 2050·1000/4095 = 1500.6 → 1501 | 1501.0 мкс |
| MIRROR, pitch = 30° → tilt | 1500 + 30·500/90 = 1666.7 → 1667 | 1667.0 мкс |
| Крок наростання tilt (300 °/с, 20 мс) | 300·500/90·0.02 = 33.3 → 33 мкс | 1533, 1566, 1599, 1632, 1665, 1667 — **крок 33 мкс** (FR-06) |

**Спостереження D1: перший імпульс після старту.** Перші імпульси мають ширину pan = 1505.75 мкс і
tilt = 1496.25 мкс, а не 1500. `HAL_TIM_PWM_Start(CH1)` вмикає вихід і лічильник, а `HAL_TIM_PWM_Start(CH2)`
виконується на 9.5 мкс пізніше, тож перший період обох каналів неповний (різниця 1505.75 − 1496.25 = 9.5 мкс).
Для серво це несуттєво: < 1° протягом 20 мс. Рішення на майбутнє — вмикати CCxE обох каналів до
`__HAL_TIM_ENABLE` (один запис у CCER).

## E. ADC і контур керування (службові GPIO)

ADC не має цифрового трафіку, тому момент вимірювання позначає службовий вихід **PB0 (PROBE_ADC)**:
1 — перед `HAL_ADC_Start`, 0 — після читання результату. **PA9 (PROBE_LOOP)** позначає межі `control_step()`.

| Параметр | Розрахунок | Виміряно |
|---|---|---|
| Період вимірювань у контурі | 20 мс | 20.0016 мс (медіана; джитер 19.06–23.93 мс, коли головний цикл зайнятий UART-виводом) |
| Час перетворення ADC (t_s + 12.5 тактів) | 2.17 мкс | маркер 38.7 мкс — це повний виклик HAL (Start + PollForConversion + GetValue + Stop), а не саме перетворення |
| Від PROBE_LOOP↑ до PROBE_ADC↑ | — | 3.0 мкс |
| Серія `cap adc` (10 замірів) | 10 мс + друк рядка ≈ 2 мс | 12.0 мс |

На реальному залізі той самий метод дозволяє виміряти дрейф ADC відносно PWM. Для синхронного семплування
перетворення варто запускати від TRGO таймера (TIM3 update), і тоді PB0 стане непотрібним.
